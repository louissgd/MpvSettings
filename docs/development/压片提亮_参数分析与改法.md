# 压片提亮：你那条命令为什么效果差，怎么改

> 针对你实际的链路：`DGSource.avs`（DGDecodeNV，HDR10 PQ）→ libplacebo → y4m → x265 HDR10。
> 2026-11-20 分析。

## 一、结论：不是 contrast 数值不够大，是参数组合用错了

你上次用的：

```
libplacebo=inverse_tonemapping=1:contrast=1.17:brightness=0:tonemapping=clip
```

这里有个硬冲突：

- **`tonemapping=clip` = 不做任何 tone mapping，PQ 码值原样输出**
- `inverse_tonemapping=1` 的作用是解除"输出峰值不得超过源峰值"的限制，让 **spline 进入逆映射分支**把 PQ 朝显示器峰值拉伸

clip 模式下根本没有 spline 映射，`inverse_tonemapping` **无处施展**。所以你实际拿到的只有 `contrast=1.17` 这一个 equalizer 增益（+17% 对比度），提亮幅度当然小。

这也解释了为什么 1.0.2 记录第九节（旧值 contrast 1.17）后来被推翻——那套值本来就指望 inverse 出力，clip 模式把它废了。

注意：1.0.3 最终定档（记录 11.3）**根本不是靠 contrast**，而是：

| 档位 | tonemapping | inverse | contrast |
|---|---|---|---|
| 关闭 | clip | no | 0 |
| 0.6 | **spline** | yes | 0 |
| 0.8 | **spline** | yes | 6 |
| 1.0 | **spline** | yes | 12 |

**没有任何一档是 clip + inverse。** 你等于把播放端明确不用的组合拿来压片了。

---

## 二、但压片不能直接照搬 1.0.3 的 spline + inverse

1.0.3 那套是**显示端实时调整**：`spline` 把 HDR 映射成 SDR 观感，专门给你那块 2000nits 显示器看。它依赖显示器的实际峰值。

你的压片目标是 **HDR10 输出**（x265 带 `smpte2084` / `bt2020` / `max-cll` / `master-display`）。一旦用 `tonemapping=spline`，libplacebo 会把 PQ 信号映射成 SDR 曲线，再用 `--transfer smpte2084` 错误地标成 HDR——**元数据与画面矛盾**，在 HDR 显示器上会发灰或过暗。

所以压 HDR 的正确思路不是搬 mpv 那套，而是：**在 PQ 域内直接做 luminance 增益/逆映射，保持输出仍是 PQ。**

---

## 三、压 HDR 真正可用的提亮旋钮

本机 ffmpeg 的 libplacebo 支持以下选项（已逐个验证接受/拒绝）：

| 选项 | 位置 | 作用 | 对你的用途 |
|---|---|---|---|
| `contrast` | 滤镜原生 | equalizer 对比度增益，默认 1 | 你已在用，幅度有限 |
| `brightness` | 滤镜原生 | -1..1，加性亮度 | 可小幅补亮 |
| `extra_opts=contrast_recovery=X` | 原生透传 | **HDR 对比恢复强度，0..3，默认 0.3** | ⭐ HDR 专用提亮，PQ 域内 |
| `extra_opts=black_cutoff=X` | 原生透传 | 黑电平裁切 | 配合暗部 |
| `peak_detect` / `percentile` | 滤镜原生 | 动态峰值检测 | 影响 tone map 基准 |
| `saturation` | 滤镜原生 | 饱和度增益 | 提亮后补色 |

`contrast_recovery` 是关键——它专门做 HDR 场景的对比度/亮度恢复，且**在 PQ 域生效，不破坏 HDR 元数据**。这正是你想要的"提亮明显"且不毁 HDR。

---

## 四、推荐改法（按优先级）

### 方案 1：先试 contrast_recovery（最小改动）

把你命令里的滤镜换成：

```
-vf "libplacebo=inverse_tonemapping=0:contrast=1.10:brightness=0:tonemapping=clip:extra_opts=contrast_recovery=2.0"
```

- 去掉无效的 `inverse_tonemapping=1`（clip 下无意义）
- contrast 从 1.17 略降到 1.10（避免高光过硬）
- 加 `contrast_recovery=2.0`（默认 0.3，这是提亮主力）
- 可再叠 `extra_opts=black_cutoff=0`

先压一个 `trim(0,100)` 短片，用你的播放器在 HDR 显示器上 A/B 看效果，逐步把 `contrast_recovery` 往 3.0 推。

### 方案 2：换 DGHDRtoSDR（你 AVS 里已经加载了这个插件）

你的 `DGSource.avs` 第 2 行就 `LoadPlugin("DGHDRtoSDR.dll")`，注释里也有现成写法：

```avs
DGHDRtoSDR(mode="hlg",white=5000,r=1,g=1,b=1,fulldepth=true)
```

但这是 **HDR→HLG/SDR**，会改 transfer。如果你能接受输出改成 HLG 或 SDR（放弃 HDR10 元数据），这个比 libplacebo 在你的环境里稳得多——它是纯 CPU 滤镜，不受 Vulkan OOM 影响。对应 x265 参数要改 `--transfer arib-std-b67`（HLG）或 `bt709`（SDR）。

### 方案 3：AVS 里用 Levels/Tweak 直接拉 PQ 码值（最土但最稳）

纯 CPU，零 Vulkan 依赖。在 AVS 里 `DGSource(...)` 后接：

```avs
Levels(0, 1.15, 65535, 0, 65535, coring=false)
```

10bit 下 gamma=1.15 提亮中间调，PQ 码值整体抬升，输出仍是 PQ。缺点是不是感知均匀提亮，高光容易压缩。适合快速试。

## 五、一个必须提醒的环境问题

本机 ffmpeg 的 libplacebo 现在**任何输入都报 `VK_ERROR_OUT_OF_DEVICE_MEMORY`**（连 64×64 的 `color` 源、申请 256K 都失败），虽然显卡空闲 9.6G。这是这个 2026-09-24 nightly 的 Vulkan allocator 与当前驱动的组合 bug，不是显存不够。

- 你上次能跑出 101 帧，说明当时 GPU 状态允许；现在复跑大概率失败。
- 试过无效：缩小 LUT、`peak_detect=0`、显式 Vulkan hwdevice、CUDA/d3d11va 继承。
- 如果 `方案 1` 现在跑不起来，别怀疑参数——直接走方案 2/3 的 CPU 路径。

## 七、2026-11-20 新版 FFmpeg 复测（用户重下后）

新构建：`ffmpeg version 2026-11-19-git-01ca75d350-full_build-www.gyan.dev`，`libplacebo v7.392.0`。
好消息：新版的 `contrast_recovery` 已经变成**原生选项**（不再需要 `extra_opts=` 透传），范围 0..3，默认 0.3。

坏消息：**libplacebo 依旧完全跑不起来**，所以 `contrast_recovery=2.0` 这次还是没能实际出帧。

### 失败证据（新版）

- 最小输入（64×64 `color` 源）直接失败：libplacebo 申请 256K 纹理时选中 `memory type 4 / heap 2`——
  这个 heap 只有 **214M**（flags 0x1，device-local，也就是 ReBAR 区），
  报 `VK_ERROR_OUT_OF_DEVICE_MEMORY`，随后 slab 分配器 `No slab to serve request for 4096 bytes` 崩掉。
  显卡总显存 12G、空闲 9.2G，**不是显存不够**。
- 显式 `-init_hw_device vulkan=vk0 -filter_hw_device vk0` + `hwupload` + `inherit_device=1`：
  帧纹理能过，但建 LUT 纹理时又以 16K 请求失败（`No slab ... in pool 1`）。
- 缩小 `tonemapping_lut_size` 到 2/16/64、关 `dithering` / `peak_detect` / `apply_filmgrain` / `apply_dolbyvision`：**都无效**。
- 真实 AVS 片段（`base.avs`，3832×1600 HDR10 PQ）跑
  `libplacebo=inherit_device=1:tonemapping=clip:contrast=1.10:contrast_recovery=2.0`：同样 252K / 8192B 分配失败。
- 旧版 `ffmpeg6.0.exe` 显式 Vulkan 也失败（`No slab ... Failed allocating vertex buffer`），
  换成 Chrome 自带的 SwiftShader ICD 也失败。**不是某一个 nightly 的回归，是这台机 Vulkan 内存堆选择的问题。**

### 可行的 CPU 替代（已实测亮度和幅度）

测试素材：`<测试片名> S02E09 ... HDR H 265-RAWR.dgi`，`DGSource + trim(0,100)`，101 帧，
`yuv420p16le / bt2020nc / bt2020 / smpte2084`，3832×1600。用 `signalstats` 读 `YAVG`（0..65535）：

### 修正后的最终建议

1. 暂时放弃 ffmpeg/libplacebo 的 `contrast_recovery`——新旧构建、软硬 Vulkan 都过不去，
   等驱动或 libplacebo 修复 ReBAR heap 选择问题后再试（BIOS 关 ReBAR 也可能有效，但代价不值得）。
2. 直接在 AVS 的 `DGSource(...)` 后、`trim` 前后都行，插入：
   ```avs

   ```
   注意 AviSynth `Levels` 的参数顺序是 `(input_low, gamma, input_high, output_low, output_high, coring)`：
   第二个值 **1.15 就是 gamma**，不是 input_high；`input_high` 保持 65535，输出范围也不变。
   gamma>1 提亮中间调。想更亮把 1.15 提到 1.20~1.25；输出仍是 PQ，HDR10 元数据不用改。

4. 测试脚本留在 `<工作目录>/lp_test/`：
   `base.avs` / `levels115.avs` / `levels125.avs`。

## 七、HDRTools 链路再查：CoeffAdj 的真相（2026-11-21）

问题：`DGSource.avs` 里的 `ConvertYUVtoLinearRGB(Color=1,OOTF=false)` +
`ConvertLinearRGBtoYUV_BT2446_A_HDRtoSDR(Lhdr=1000.0,CoeffAdj=0.8)`，
`CoeffAdj=0.8` 是用户自测出来的（ Harris 官方示例里是 1.0）。是不是作者把函数名写错、
或者用户理解错了"PQ 进 PQ 出"？源码仓库：github.com/jpsdr/HDRTools（已克隆到 `lp_test/HDRTools_src`）。

### 源码事实

1. **函数名没写错**。`CoeffAdj` 是作者有意加的私有参数，ReadMe 第 791-794 行原文：
   `CoeffAdj - This is not part of BT2446 A method, added, multiply the data by the value. Default: 1.0`
   —— 明确说"这不是 BT.2446 Method A 的一部分，是我加的，把数据乘以这个值"。
   所以示例里是 1.0（=不改变），刻意不放进标准流程。
2. **乘的位置**：`HDRTools.cpp:12107` `alpha=1/2.4`，12127-12129：
   `R = min(powf(CoeffAdj*srcR, 1/2.4), 1)`；LUT 版 28358 同理
   `lookupEOTF_16[i] = round(65535 * min(pow(CoeffAdj*x, 1/2.4), 1))`。
   即 CoeffAdj 在 **RGB 线性域、BT2446 的 pow(1/2.4) 之前**相乘，然后进 tone map。
3. **Color=1 不是 PQ**。ReadMe 第 47-55 行：0=BT2100（PQ/HLG），1=BT2020，2=BT709。
   源码 16094-16106 / 16038-16105：`Color!=0` 且 `EOTF=true,OOTF=false` 时走
   `x = pow(x, coeff_p)`（普通 gamma EOTF，coeff_p≈2.4），**根本不是 PQ_EOTF**。
   PQ_EOTF 只在 `Color==0 && HDRMode==0` 分支（16004-16012）。
   所以 `Color=1,OOTF=false` 这一句输出的是 **BT2020 gamma 线性光，不是 PQ**。
4. 反过来，BT2446_A_HDRtoSDR 这条链是 **HDR→SDR** 色调映射（函数名和 ReadMe 779 行都写明），
   输出 `dstY=4096+Y*56064`（limited range）。结束之后是 SDR YUV，**不是 PQ**。

### 实测（<测试片名> HDR10，101 帧，signalstats 平均亮度，0..65535）

| AVS 链路 | 平均亮度 | 相对原片 | 相对 CoeffAdj=1.0 |
|---|---:|---:|---:|
| 原片 DGSource（PQ 码值直接读） | 18415.5 | — | — |
| Color=1 + BT2446_A HDRtoSDR, CoeffAdj=0.8 | 22758.3 | +23.6% | −6.2% |
| Color=1 + BT2446_A HDRtoSDR, CoeffAdj=1.0 | 24271.0 | +31.9% | — |
| Color=1 + BT2446_A HDRtoSDR, CoeffAdj=1.2 | 25581.8 | +38.9% | +5.4% |

### 结论

- **作者没写错，是你理解反了两处：**
  1. `CoeffAdj=0.8` 不是"提亮"，是**压暗**——它是乘性系数，实测从 0.8→1.2 单调递增，
     0.8 比默认 1.0 暗 6.2%。你看到的"提亮"来自整条 HDR→SDR 链路本身（+23.6%），
     不是 0.8 这个数；0.8 是在已经提亮的结果上再压回去一点。
  2. 这条链**不是 PQ 进 PQ 出**。进去：`Color=1` 走 gamma EOTF（BT2020），
     不是 PQ 解码（PQ 要 `Color=0,HDRMode=0`）；出来：BT2446 Method A 是
     HDR→SDR tone map，输出 SDR limited range。所以这是一条 **gamma 域的 HDR→SDR 转换**，
     只是"看起来"用了 HDR 源。之所以能直接压片提亮，是因为把 HDR 码值当 gamma 数据
     做 SDR 映射，码值整体抬高了——本质是"用 SDR 映射改码值"而非 PQ 域调光。
- **如果你想要真正的 PQ 进 PQ 出**，别用这条链。PQ 域调光应走
  `ConvertYUVtoLinearRGB(Color=0,HDRMode=0,OOTF=false)` + 线性域乘法 +
  `ConvertLinearRGBtoYUV(Color=0,HDRMode=0,OOTF=false)`，或直接在 AVS 里用
  `Levels(0,gamma,65535,0,65535,coring=false)` 这类码值域调整，HDR10 元数据保持不变。
- 测试脚本：`lp_test/ch08.avs`、`ch10.avs`、`ch12.avs`（HDRTools.dll 在
  `<项目根>/02.AVS+/plugins64+`）；源码克隆在 `lp_test/HDRTools_src`。

### 补查：为什么预览"发灰"——元数据错配（2026-11-21 二轮）

用户反馈：直接预览 AVS，加 CoeffAdj 和不加都是"灰色"，明度有区别，但都不是 SDR 画面。
这不是错觉，实测抓到了根因：

- ffmpeg 读 `ch08/ch10/ch12.avs` 的流信息全是
  `yuv420p16le(tv, bt2020nc/bt2020/smpte2084, progressive)`——
  **传输函数标签仍是 `smpte2084`（PQ）**，色域仍是 BT2020。
- 但 `ConvertLinearRGBtoYUV_BT2446_A_HDRtoSDR` 输出的像素已经是 **SDR gamma 码值**
  （源码 `dstY=4096+Y*56064`，Y 经 BT2446 的 `pow(pSDR,Yc)` 回到 SDR 域）。
- AVS 滤镜不改写 frame 的色彩元数据，PQ 标签从 DGSource 一路沿用下来。

于是形成**三重错配**，这才是"灰"的来源：

| 环节 | 应有的数据 | 实际发生 |
|---|---|---|
| 输入解码 | PQ 码值 → PQ_EOTF → 线性光 | `Color=1` 是 BT2020，走 `pow(x,0.45)` 普通 gamma 分支（源码 16094-16106），**根本没走 PQ_EOTF**（PQ 只在 `Color==0,HDRMode==0` 的 16004-16012） |
| tone map | HDR 线性光 → SDR | BT2446 Method A 确实是 HDR→SDR，但喂进去的"线性光"是拿 PQ 码值当 gamma 解出来的，暗部被抬平 |
| 输出标记 | SDR 码值应标 bt709/bt1886 | 仍是 `smpte2084`(PQ)；播放器按 PQ EOTF 显示 SDR gamma 码值 → 中间调被压暗、低对比、发灰 |

**为什么"加参数不加参数都灰、只有明度不同"**：`CoeffAdj` 只是在 BT2446 的 `pow(1/2.4)`
之前乘一个线性增益（源码 12127），它改明度，但不改传递函数、不改曲线形状、不修元数据。
所以灰的本质（标签错配 + 输入解错）永远不变，只有亮度档位在动——与观察完全一致。

**为什么"调整后看起来不错"**：`CoeffAdj=0.8` 恰好把 tone map 后的码值压到一个讨喜的
亮度档，加上 BT2446 的 S 曲线把高光柔化，视觉上舒服。这是歪打正着，不是正确的 HDR 处理。
用 AVS 预览器（通常按 gamma 显示码值、不看 HDR 标签）看会觉得"像正常 SDR"；
但压成 x265 后元数据继承 PQ，在 HDR 设备上会发灰发暗。

**要真正的 PQ 进 PQ 出**：两端都用 BT2100/PQ 通道——
`ConvertYUVtoLinearRGB(Color=0,HDRMode=0,OOTF=false)` → 线性域乘增益 →
`ConvertLinearRGBtoYUV(Color=0,HDRMode=0,OOTF=false)`；或最省事，直接在 PQ 码值域
`Levels(0,gamma,65535,0,65535,coring=false)`，HDR10 元数据原样保留。

---

## 六、一句话

你用了 `clip + inverse` 这个播放端明确不用的组合，inverse 被 clip 废掉，只剩 +17% 对比度，所以提亮不明显。压 HDR 别搬 1.0.3 的 spline（会毁 HDR 元数据），改用 PQ 域内的 `contrast_recovery`（默认 0.3→试 2.0~3.0）；若 libplacebo 因 Vulkan bug 跑不动，就用你 AVS 里现成的 DGHDRtoSDR 或 Levels。
