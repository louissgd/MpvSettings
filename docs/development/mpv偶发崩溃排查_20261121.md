# mpv 偶发崩溃排查（2026-11-21，2026-11-24 三次翻案）

## ★★★ 最终结论（2026-11-24，取代下方全部版本）

**用户新线索：崩溃视频基本都是 1080P 以下。A/B 实测证实——分辨率是强变量，
但根因不是 `nvidia-true-hdr`，也不是 VSR 共挂，而是 `d3d11vpp` 本身在
小尺寸帧上初始化就会崩；VSR 和 HDR 两路都中招。**

### 决定性实验（`_verify/rtx_crash_ab.py` + `abtest_toggle.lua`）

同片源反复切换 window-scale 制造 d3d11vpp 挂载，每组独立进程，统计 0xC0000005 退出码：

| 片源 | 全关 | 纯 VSR | 纯 HDR | VSR+HDR |
|---|---|---|---|---|
| 720×480 DVD（`911 - A Night To Remember.vob`） | **0/20** | 10/20 | 11/20 | 10/20 |
| 1920×1080 VP9（Marching Season） | — | 0/12 | 0/20 | 0/20 |

- 低分辨率下三路 RTX 组合崩溃率一致（~50%），全关归零 → **d3d11vpp 是必要条件，
  nvidia-true-hdr 不是**。11-21 定的「RTX HDR 这一路」结论范围过窄。
- 所有崩溃都发生在 `mounts=1`（首次挂载那一刻）；活下来的跑完 22 次挂卸无碍 →
  小尺寸帧初始化是危险点，不是挂卸次数。
- 1080P 片在 VSR+HDR 共挂下反复挂 446 次零崩 → 分辨率才是分界线。

### 修复：RTX 最低分辨率（`rtx_min_res`）

- `MyMPC_ui.lua` 新增 `rtx_min_res`（默认 `720p`），按**短边**判定，VSR 和 HDR 两路
  共用同一条下限：`rtx_big_enough = min(w,h) >= 阈值`。低于档位时 d3d11vpp 完全不挂。
- 档位 `off|sd|720p|1080p|1440p`，`off` = 恢复旧行为（逃生口）。
- 设置程序：`SettingsDraft.RtxMinResIndex`（默认 2=720p）、`WritePlanBuilder` 写
  `rtx_min_res`、`VideoView.xaml` 加「RTX 最低分辨率」下拉；状态说明同步改写。
- 验证：DVD 0/16 崩（hdr=0 vsr=0），1080P 0/8 崩（hdr=120 vsr=56）；
  `stage2_verify.py` 94 项全过，`dotnet build` 0 警告 0 错误。

**结论：不再需要「接受偶发」。DVD/VCD 默认不碰 d3d11vpp，崩溃路径被绕开。**

## ★★ 旧结论（01:35 二次翻案，已被 11-24 三次翻案取代，保留作推理存档）

**根因修正：不是 `target-colorspace-hint`，是 RTX HDR（`d3d11vpp nvidia-true-hdr`）
这一路动态挂载本身。`hint` 只是间接开关——它通过「能否让 `video-target-params`
协商出 pq」控制 HDR 判据是否成立；HDR 一旦真挂上，hint 取 yes/auto/no 崩溃率无差别。**

**用户诉求**：RTX HDR 必须保留，崩溃只是偶发，只需测 `auto` 能否规避。
**答案：不能。auto 无效，且 hint 这一路整体不是根因。**

### 决定性实验（01:24-01:35，Python subprocess 独立跑，exit 3221225477=崩）

**实验1 —— 抓日志看 HDR 到底挂没挂**（`hdr_mount_probe.py`）：

| hint | `[MyMPC/rtx] RTX-HDR` 日志 | `Tagging image output as HDR` |
|---|---|---|
| yes（默认） | 有 | 有 → 崩（4/4） |
| auto | 有 | 有 → 崩（3/4） |
| no | **无** | **无** → 不崩 |

关键：`hint=no` 时 RTX HDR **根本没挂上**（判据 `desktop_hdr` 依赖
`video-target-params/gamma=="pq"`，hint=no 后协商不出 pq，判据失败）。
所以之前「关 hint 0/5 不崩」是假象——它把 HDR 一起关了，对「必须保留 RTX HDR」
的诉求无效。

**实验2 —— 临时配置去掉 `desktop_hdr` 判据，强制三种 hint 都挂上 HDR**（`hint_compare.py`）：

| hint（HDR 均挂上 5/5） | 崩溃率 |
|---|---|
| yes | 2/5 |
| **auto** | **3/5** |
| no | 2/5 |

三者无本质差别（~40-60%，自动化高频触发下）。**证明 hint 值不是根因。**

**实验3 —— 尽早挂载（0.05s + 去掉 `video-target-params` 观察触发）**（`rtx_decouple_test.py`）：
HDR 6/6 挂上，仍崩 2/6。调整挂载时机同样无效。

### 关于「2 秒延迟」和「MPCVR 从不这样」

- RTX HDR 的开启判据（脚本 431-434 行）依赖 `video-target-params/gamma=="pq"`
  ——即 mpv 协商出的**输出色彩空间**。这个属性比 `file-loaded` 晚到；
  脚本里 `file-loaded` 0.25s 先判一次、1s 兜底再判，`observe video-target-params`
  再触发。你说的「2 秒后才变亮」就是**在等这次色彩协商完成**，判据成立才挂 HDR。
- MPCVR 没有这延迟，是因为它的 RTX HDR 是渲染器**内建开关**，播放初始化时
  一次性配置；而 mpv 的 `nvidia-true-hdr` 是外部 `vf`，必须等协商出结果才能
  动态挂上——架构差异，不是配置问题。
- 这也解释了「偶发」：只要 HDR 挂着，D3D11 渲染线程在色彩协商/VO 重建敏感期
  动态挂卸 `d3d11vpp` 就有空指针概率；撞上就崩，撞不上就正常。和截图经常一起崩
  也是同理（截图触发 VO 重建）。

### 给用户的选择（RTX HDR 保留前提下）

1. **维持现状**（用户倾向）：接受偶发。hint=yes 保持不动，不必改 auto（已证无效）。
2. **降低概率（未验证收益）**：`target-colorspace-hint=no` + 脚本去掉 `desktop_hdr`
   判据（改成 `local hdr = o.rtx_hdr and is_sdr`）。能让 HDR 在 hint=no 下也挂上，
   崩溃率从「默认 4/4」降到「2/5」左右，但非零、且牺牲了协商正确性。不建议为偶发
   引入这个复杂度。
3. **根治**：等 mpv 上游修 `d3d11vpp`/libplacebo 这个空指针（issue #17800 追踪），
   或换用 MPCVR 那套内建实现。

**生产脚本未被任何实验改动**：两处 `MyMPC_ui.lua` MD5 仍为 `3a86ffc3`（01:00 防抖版）。
实验全在工作目录 `lp_test/` 的临时副本中完成，已清理。

## ★ 旧结论（01:20，已被上方二次翻案推翻，保留作推理存档）

**当时判断：`vo=gpu-next` 的 `target-colorspace-hint=yes` 与 d3d11vpp 的 RTX Video HDR

证据链：
1. **反汇编崩溃点**：`mpv.exe+0x248CE63` 落在 libplacebo 的 GPU 纹理/像素格式代码
   （附近字符串 `2bgr10be`、`m_state.planes[PLANE_Y].format.type == PixelType::FLOAT`、
   `TEXTURE2DARRAY`）；调用栈返回地址反汇编显示 `mpv player → vo_gpu_next →
   libplacebo texture`（`call 0x...1781960`，栈上有 `watch_later`/`video EOF reached`
   等 player 层字符串）。异常恒为 READ at 0xFFFFFFFFFFFFFFFF。
2. **A/B 实测**（那个 MPG，Python subprocess 独立跑，各 4-6 次，exit 139=崩）：
   | 组合 | 崩溃率 |
   |---|---|
   | 默认：RTX HDR 开 + hint 开 | **4/4**（另一轮 3/6） |
   | 关 `target-colorspace-hint`（RTX 保持开） | 0/5 |
   | 关 RTX（`--script-opts=...rtx_vsr=no,rtx_hdr=no`，hint 保持开） | 0/4 |
   | 换 `vo=gpu`（老渲染器） | 0/1 |
   单关任一方即不崩 = 两者组合触发。VSR 未参与（720x576 源 zoom=1 不挂）。
3. **网上佐证**：
   - mpv issue #17800「nvidia-true-hdr should not take effect in SDR display or HDR source」：
     官方确认 `nvidia-true-hdr` + `gpu-next` + 色彩空间转换存在内部处理错误。
   - mpv issue #12666 / #17103：`--vo=gpu-next --target-colorspace-hint=yes` 单独即可
     在退出/HDR 输出时段错误，`vo=gpu` 不复现。
   - 官方 PR **#18199**（kasper93，2026-06-28 **已合并进 master**）：
     `vf_d3d11vpp: enable NVIDIA RTX Video only for SDR input`，让 HDR 源不再误走
     nvidia-true-hdr。用户版本 v0.42.0-94 (Nov 16) 晚于该合并但仍崩，说明该 PR
     只修"HDR 源误触发"，**未覆盖本例的 hint+RTX-HDR 崩溃**。

**推荐修法（按优先级，均未改动、待用户定夺）**：
- **A（最稳，推荐）**：`mpv.conf` 把 `target-colorspace-hint=yes` 改成 `no`。
  A/B 已证 0/5 崩。代价：Windows HDR 下 SDR→HDR 的 EDR/passthrough 效果没了；
  但本机本就靠 d3d11vpp 的 RTX HDR 做 SDR→HDR，hint 属重复且冲突。
- **B（保留 HDR 映射，官方写法）**：改用条件 profile，仅在 RTX HDR 生效时把 hint
  设为 `auto` 而非 `yes`（来自 issue #17800 官方建议）：
  ```ini
  [RTX-HDR]
  profile-cond=get("video-params/gamma") == "bt.1886" and get("video-target-params/max-luma") > 203 and p.current_vo == "gpu-next"
  profile-restore=copy
  inverse-tone-mapping=no
  target-colorspace-hint=auto
  ```
  仍需实测 `auto` 是否规避本例崩溃（本例只测了 yes/no）。
- **C（放弃 RTX HDR）**：`script-opts/MyMPC.conf` 里 `rtx_hdr=no`，A/B 已证 0/4 崩。
- **D**：换回 `vo=gpu`，但会失去 libplacebo 的色调映射质量，不推荐。

**关于 01:00 那次 apply_rtx 防抖改动**：方向错了，但无害（减少无谓的滤镜挂卸）。
可保留，也可回退（备份在 `lp_test/rtxfix_bak/`）。它不影响上述崩溃。

## 现象
- 播放 `D:\Video\Ronan Keating - This I Promise You (MixMash).MPG` 偶发崩溃，非必现。
- 用户反馈：昨天测试截图时也经常崩溃。

  ffmpeg 全片 5676 帧解码零错误。

## 硬证据（Windows 事件日志 + 9 个 crash dump）
- 异常：`0xC0000005` 访问违例，参数 `[0xFFFFFFFFFFFFFFFF, 0x0]` = **空指针解引用**。
- 崩溃模块：**mpv.exe 自身**（不是 d3d11.dll / NVIDIA 驱动直接崩）。
- 崩溃偏移：9 个 dump 中 **8 个在 `mpv.exe+0x248CE63`**，1 个在 `+0x1E10385`。
  高度集中 = 稳定的代码路径缺陷，不是随机内存损坏。
- 故障进程：`C:\Users\Administrator\MyMPC\MediaPlayer\mpv\mpv.exe`
  版本 v0.42.0-94-g543a8c2c5-**dirty**（打过补丁的自建版，libplacebo v7.396-dirty）。
- dump 里出现的模块含 `d3d11.dll`、`nvwgf2umx.dll`、`nvppex.dll`、`d3dcompiler_47.dll`
  ——崩溃发生在 D3D11 渲染/视频处理线程栈上。
- 复现时日志：`[d3d11vpp] Tagging image output as HDR with max-luma=1000 nits for NVIDIA RTX Video HDR...`

## 最可能根因：rtx 滤镜动态挂卸竞态

`portable_config/scripts/MyMPC_ui.lua` 的 `apply_rtx()`（第 362-468 行）在运行时
动态 `vf add/remove d3d11vpp`。它被 **6 处**触发，且都用 `mp.add_timeout(0.1~1.0)` 延迟排队：

- file-loaded → 两个 timeout（0.25s / 1.0s）
- observe `video-params`（0.1s）
- observe `hwdec-current`（0.1s）
- observe `window-scale`（0.15s）
- observe `fullscreen`（0.2s）
- observe `video-target-params`（0.1s）

问题：
1. `rtx_applying` 只锁住单次 `apply_rtx()` 内部的同步执行，**锁不住这些 timeout 之间**。
   它们排在不同时刻各自执行，每个都可能走到 `rtx_remove()` → `vf remove`。
2. `vf remove/add d3d11vpp` 会重建滤镜链和 D3D11 视频处理器。
3. 截图 / VO 重建正好也在动渲染链。几方撞在一起，d3d11vpp 拿到已释放的 frame
   → 空指针 → 崩溃。这解释了"偶发"和"截图时也崩"。

副证：函数注释里自己记录了过去多次竞态翻车（osd 正反馈滚到 scale=8.5、
"放大两次"、IPC 时间线探针），说明这段动态滤镜逻辑本来就脆弱。

## 次要怀疑
- 第二个偏移 `+0x1E10385` 是另一处空指针，可能与主因不同，但同样在 mpv.exe。
- 崩溃偏移跨 11-20 / 11-21 固定不变，说明不是配置最近改动引入，是长期存在的隐患。

## 建议（按优先级）

1. **先验证根因**：把 `script-opts/MyMPC.conf` 里 `rtx_vsr` 和 `rtx_hdr` 都改成 `no`，
   正常使用 + 截图一段时间，看崩溃是否消失。备份在
   `MyMPC.conf.bak_crash_20261121_0053`。这是最快的证实/证伪手段。
2. **若确认**：修 `apply_rtx()` 的竞态——给所有 `mp.add_timeout` 回调加一个统一的
   防抖（debounce）：只保留最后一次触发，取消前一个 pending timer；并在
   `rtx_remove()` 用 `pcall` 包住 `vf remove`。不要在截图/VO 重建期间挂卸滤镜。
3. **治本**：这个 mpv 是 `-dirty` 自建版，但没有 RTX 补丁——`d3d11vpp` 的
   `nvidia-true-hdr` / `scaling-mode=nvidia` 是 mpv 0.40+ 上游自带功能，
   `-dirty` 只是本地其他改动。没有 PDB 无法把空指针符号化到源码行；若要深挖，
   需要给自建 mpv 生成 PDB 并保留，再用 WinDbg `!analyze -v` 看
   `mpv.exe+0x248CE63` 的具体函数。
4. **临时规避**：不需要 RTX VSR/HDR 时直接关掉这两个开关，崩溃概率应显著下降。

## 2026-11-21 已实施修复（待 1~2 天实测确认）

按用户要求，先按建议 2 改 `apply_rtx()` 的竞态，RTX 功能逻辑不动，交由实机验证。
改动文件两处、内容完全一致：

| 文件 | 修复前 MD5 | 修复后 MD5 |
|---|---|---|
| `生产 mpv/portable_config/scripts/MyMPC_ui.lua` | `1e3b065a...` | `3a86ffc3...` |
| `D:\MyMPC_CG_x64\12.mpv\portable_config\scripts\MyMPC_ui.lua` | `1e3b065a...` | `3a86ffc3...` |

备份（打包目录之外，符合备份约定）：
`lp_test/rtxfix_bak/MyMPC_ui.lua.prod_20261121_0102`、
`lp_test/rtxfix_bak/MyMPC_ui.lua.12mpv_20261121_0102`。

改动明细：
1. 新增 `local rtx_timer` + `schedule_apply_rtx(delay)`：所有触发源共用**单个** timer，
   每次调度先 `rtx_timer:kill()` 取消上一个 pending，只保留最后一次意图（防抖）。
   原来 6 个 observer + 2 个 file-loaded timeout 各自排队、互不互斥的问题被消除。
2. 6 个触发点全部改用 `schedule_apply_rtx(...)`（0.15~0.2s），不再直接
   `mp.add_timeout(..., apply_rtx)`。
3. `file-loaded` 的 1s 兜底改为幂等：只在 `rtx_filter == nil`（还没挂上）时才补判，
   挂对了直接跳过，不再额外制造一轮 `vf remove/add`。
4. `end-file` 先 cancel pending timer 再 `rtx_remove()`，避免换片瞬间残留回调。
5. `rtx_remove()` 里两条 `vf remove` 用 `pcall` 包住，滤镜已被 VO 清掉时不致 Lua 抛错。

验证：mpv 加载脚本无 Lua 错误；API 探针确认 `timer:kill()` 在本机 mpv 可用；
两处副本 MD5 一致；无残留裸露 `add_timeout(..., apply_rtx)`。

**待用户实测**：保持 `rtx_vsr` / `rtx_hdr` 原样（不要关），正常使用 + 频繁截图 1~2 天。
- 若崩溃消失 → 竞态根因确认，修复保留。
- 若仍崩溃 → 说明空指针另有出处，回退备份后走建议 3（自建 mpv 出 PDB 符号化），
